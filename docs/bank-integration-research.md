# Zambia bank integration research

Reviewed 7 September 2026. The employer has no bank API or host-to-host access yet. No bank application has been submitted and no live account is connected.

## Coverage and findings

The [Bank of Zambia deposit-insurance notice](https://www.boz.zm/Public_Notice_Deposit_Insurance_Scheme.pdf) identifies 15 commercial banks; the [registered-bank list](https://www.boz.zm/Registered_Banks_November2025.pdf) supplies the institutions covered below. This is a bank access guide, not a claim of 15 implemented connectors. Public marketing is evidence of a channel to discuss, not a technical contract or an entitlement.

One employer funding bank can support salaries to other banks: [Zanaco PayFlexi](https://www.zanaco.co.zm/business-banking/electronic-banking/) explicitly describes this. Separate account feeds require access to each employer's accounts at the relevant banks. We therefore cover every recipient bank while onboarding each actual funding account through its bank.

Group API portals and regional pages do not prove Zambia/ZMW product availability. This qualification particularly affects FNB Integration Channel, CitiConnect, Ecobank APIs and Access PrimusPlus. Absa merchant card host-to-host information must not be treated as payroll integration documentation. No public API specification found means exactly that; it does not prove the bank has no private integration service.

## Onboarding pack to request

These are proposed questions and documents to agree with each bank, not a claim that every bank has identical requirements:

- A business funding account and the bank’s mandate for each employer using ZamPayroll.
- The bank’s application, business verification documents, authorised signatories and payment approval limits.
- Written Zambia/ZMW eligibility for salary payments, interbank transfers, account feeds and third-party payroll software.
- Approved API or host-to-host specifications, test access, payment schemas and itemised statement samples.
- The bank’s required authentication and secure exchange of credentials or certificates, kept on the server.
- Agreed fees, transaction limits, cut-off times, settlement windows, returns and support contacts.
- Bank testing and production approval, including duplicate requests, partial failures and reconciliation.

Ask for the bank's current business-verification checklist, application, company registration/tax documents as applicable, authorised signatories and mandates. Confirm whether a multi-company software vendor needs separate due diligence or regulatory authorisation; this research makes no legal determination. Obtain commercial terms directly: no fee, cut-off, limit or implementation timeline is assumed.

Technical access must specify the supported API, host-to-host/SFTP or bank-upload channel; Zambia endpoints and schema versions; employer/account entitlements; authentication, signing and encryption requirements; sandbox data; status queries and duplicate protection; batch itemisation; returns/reversals; statement formats and verified callbacks. OAuth, certificates, signing keys and IP allowlists are channel-specific questions, not universal requirements. Use the bank's approved secure channel for credentials, never employee internet-banking passwords.

**Bank batches → Bank access** provides a bank-specific text brief for the employer to send. Downloading it does not contact the bank or create access. The next external dependency is a bank technical contact and an approved onboarding/specification pack.

## Implemented now

- Access guide and downloadable request briefs for all 15 banks, with public source links and explicit disconnected status.
- Existing salary-file workspace: the published FNB Zambia CSV layout and reviewed company-defined export templates. Other banks' production file layouts must be obtained and reviewed before use. No generic CSV is claimed to be accepted by every bank.
- Finalized payroll payment instructions with a stable 20-character alphanumeric reference for each company, payroll period and employee. Generated salary-template references use the same value.
- Normalized uploaded-statement review against frozen finalized payroll, with exact reference, signed debit amount and ZMW currency checks, and a downloadable review CSV.

There is no payment initiation, automatic feed, credential storage, connection profile, bank callback receiver or persistent payment-status register in this stage. No migration or new environment variable is required. Uploaded content is processed in memory and is not saved; results are not a bank confirmation and never change payroll or mark salaries paid.

## Statement preparation and limits

Use **Bank batches → Reconciliation**, select the employer's funding bank and finalized payroll, download the header-only template and map the bank's itemised statement to these columns:

`transactionId,bookingDate,reference,amount,currency`

Preserve source transaction IDs and payment references as text. Dates use YYYY-MM-DD; signed amounts have exactly two decimal places, with debits negative and credits positive. Currency must be ZMW. Select a statement date range containing all uploaded entries, including later returns or reversals. The application cannot authenticate an upload, verify its account ownership or completeness, or detect a reversal omitted from the file. Check those against the original bank statement.

Limits are 500 KB and 5,000 statement rows. Duplicate transaction IDs, invalid dates, entries outside the selected range, unsupported currency and ambiguous headers are rejected. One exact referenced debit matches; no entry is missing; differing amounts/directions and multiple entries are exceptions. A debit plus reversal is an exception. Zero net pay needs no debit. Fees and unrelated entries remain unmatched. Consolidated batch debits cannot establish individual salary settlement without bank itemisation. Matching uses integer money arithmetic, not floating-point tolerances or name guesses.

The page previews the first 100 expected payments/results and provides the full review download. Payroll selection currently covers the latest 100 runs. Reviews are transient and must be downloaded if needed for records. They require reports.read permission, tenant authorisation and CSRF on review/export POSTs; CSV text cells are escaped against spreadsheet formulas.

Payment references changed with this release. Existing downloaded salary files are not rewritten; an old bank submission with another reference needs manual reconciliation against that original file. Do not resubmit payroll simply to obtain the new reference. The reference is a matching identifier, not an implemented bank idempotency guarantee.

## Next implementation after access

Build and certify the first employer funding-bank adapter against the actual bank specifications, then extend using the other banks' approved contracts. Keep provider credentials on the server and scope account access to the authorised employer. Before any live initiation, implement persisted batches/items, a reviewed approval workflow, durable idempotency, timeout/status recovery, verified bank notifications, statement ingestion, returns and reconciliation audit records. Distinguish prepared, approved, submitted, pending, settled, rejected and reversed states according to bank evidence; an HTTP success alone must not mark salary settlement.

Acceptance must exercise partial rejection, duplicate submissions, timeouts before/after acceptance, out-of-order notifications, altered callbacks, expired credentials, holidays/cut-offs, consolidated debits and reversals. Actual settlement and release permissions must remain bank-approved and company-authorised. These are future acceptance requirements, not implemented connector capabilities.
